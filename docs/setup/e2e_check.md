# 2.1.3 — проверка правила пробега глазами пользователя

Трек: все четыре случая — 399999, 400000, 400001 (Т/А/Л) и 600000 (Р).

## Подготовка

1. Сервис поднят `docker compose up -d --build` (Docker Desktop 29.8.2, Windows).
2. `curl -i http://localhost:8080/health` → `HTTP/1.1 200 OK`, тело `{"status":"ok","service":"carmoney-lab"}`.
3. Браузер — встроенный браузер Cursor (Chromium, управление через MCP `cursor-ide-browser`),
   а не `@playwright/mcp` из Kilo: прогон делал агент Cursor. Сервер Playwright в `kilo.jsonc` прописан,
   но через Kilo этот прогон не выполнялся.
4. Для каждого случая страница `http://localhost:8080/` открывалась заново, менялось только поле
   «Пробег, км». Остальные поля — значения по умолчанию: `CL-0025`, `XTA21099998765432`, `2019`,
   стоимость `900000`, сумма `450000`, срок `24` (LTV 50 % — по LTV это approve).

## Что пошло не так по ходу (честно)

- Первая отправка (400001) прошла кликом по кнопке «Отправить заявку».
- Дальше клики инструмента по кнопке (по ref, по координатам, Enter, `button.click()`) перестали
  вызывать событие `submit`: перехват `fetch` на странице показал пустой лог, номер заявки не менялся.
  Первая попытка 600000 поэтому показала старый результат от 400001 (заявка 25) — этот скриншот выброшен.
- Обход: форма отправлялась через `form.requestSubmit()` — тот же обработчик `submit` из `frontend/app.js`,
  тот же запрос `POST /api/applications`. Это сделано для 600000, 399999, 400000 и повторного 400001.
- Одна попытка 400001 прервалась после открытия страницы, и форма ушла с пробегом по умолчанию 84000
  (заявка 28, `approve`). В отчёт не входит.

## Сверка с кодом

| Пробег | По коду (`rules.php`, `AssessmentService`, `ApplicationValidator`) | Показала система | Совпало |
|---|---|---|---|
| 399999 | approve | approve | да |
| 400000 | approve (порог строгий, `>`) | approve | да |
| 400001 | review, лимит 0 | review, лимит 0 ₽ | да |
| 600000 | 422, `Пробег от 0 до 500000 км` | «Заявка не принята», `mileage: Пробег от 0 до 500000 км` | да |

Расхождений решения с кодом нет. Расхождение с ожиданием пользователя есть:

- На 400001 пользователь видит только `REVIEW` и лимит `0 ₽`. Причина (высокий пробег) не показана;
  с review по LTV (60–85 %) это на экране неотличимо.
- В сообщении об ошибке поле названо техническим ключом `mileage`, а не «Пробег, км».

## ★ Второе место, где правило видно пользователю

Кнопка «Только рассчитать LTV» (`POST /api/ltv`) с пробегом 400001 — `docs/setup/case_400001_ltv_only.png`:

- Решение: `review`
- LTV: `50 %`
- Одобренный лимит: `0 ₽`
- Номер заявки: `не сохранена`

То есть правило пробега срабатывает и в «расчёте без сохранения». Третье место — валидация
при пробеге > 500000 (случай 600000 выше).
